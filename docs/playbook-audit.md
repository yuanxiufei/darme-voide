## 一、它到底是什么

## 二、为什么现在必须消化：原始铁律正在消失

`combat/打戏系统资料索引.md` 里 20 余条 `RULE-*`（15 秒铁律、气爆五档、有效中景裁切、
镜头衔接链、破招放大、执行层净化……）的"文件"一栏**全写 `SKILL.md`**，而两个来源目录下
**一个 `SKILL.md` 都没有**（课程包清理时带走了）。

也就是说：那套打戏系统最值钱的部分——全部铁律正文——**唯一存留形态是
`打戏系统交接包.md`（28.5 KB）里的转述**。索引本身已成空指针。

这不是"资料很丰富可以慢慢看"，而是"再放一轮就可能只剩标题"。所以本轮先消化打戏这条线。

## 四、明确拒绝移植的（附理由）

| 拒收内容 | 理由 |
|---|---|
| 15 秒 / 30 秒打戏时长体系（一镜 1.5 秒、30 秒必须拆两条提示词） | 短视频口径，与本仓**单镜 5 秒**、单集 90–195 秒直接冲突。硬搬会把分镜切碎 |

| `能量环境` / `能量击中` 的**原句**（"凌厉斩击，银白色剑气撕裂空气……"） | 那是素材作者的提示词原文，直接搬属照抄（`THIRD_PARTY_NOTICES.md` §六 红线）；只提炼为**元素—色彩对照**与**特效类别词** |
| 把 137 份复制进 `剧本知识库/` | methods 源是供应商预建的 sqlite fts5 索引（5403 部），**复制文件不重建索引** ⇒ 盘上 5403+N、索引 5403，变成两本账。`script_library.py` 抬头"只读：不重建、不写入、不复制"就是这个理由 |

## 八、目录扁平化（2026-11-04）

**问题**：最深一条路径是
`corpus/playbook/packs/film-expert-bridge/references/library/combat/战场场景库/x.md` —— 从仓库根
算 9 段、6 层目录，而其中 `packs/`／`references/`／`library/` 三层对检索与理解都没有贡献。
`references/` 尤其坏：它和判据层 `app/skills/*/references/` **同名不同义**，最容易被认错。

**做法**：把素材包名提到 playbook 根下一级，`PLAYBOOK_DIRS` 由 `("packs",)` 改成
`("film-expert-bridge", "film-cinedance")`。**目录名从此就是 `skill=` 取值**，`_skill_of()`
直接取路径第一段，不再需要「认壳、取第二段」。

| | 扁平化前 | 扁平化后 |
|---|---|---|
| 最深文件 | `packs/film-expert-bridge/references/library/combat/战场场景库/x.md`（6 层目录） | `film-expert-bridge/combat/战场场景库/x.md`（3 层目录） |
| 仓库根下段数 | 9 | 6 |
| 目录总数 | 7 层含 1 个空目录（`agents/`） | 3 层，无空目录 |
| `skill=` 取值 | `packs/` 下第二段 | 根下第一段（**对外值不变**） |
| 份数 / 小节 | 137 / 2333 | 137 / 2333（只换位置，内容一字未改） |

**改造中最容易静默出错的一处**：`_skill_arg()` 原来的前缀表写的是
`(*PLAYBOOK_DIRS, "skills")`。`PLAYBOOK_DIRS` 一旦从壳名变成技能名本身，这行会把
`film-expert-bridge/x` 当成「壳/技能名」剥掉而返回 `x` —— 过滤全失效且**不报错**。
故新立 `PLAYBOOK_SHELLS = ("packs", "skills")` 专管旧形状归一，并在注释里写明不许并回去。

**兼容边界**：`skill="packs/xxx"`、`skill="skills/xxx"` 仍归一成技能名（调用方手里的提示词、
旧会话记录、上游文档都还是这两种形状）；**`path=` 不兼容** —— 检索结果现在回新形状，
手抄旧路径会被判越界、`_playbook_target()` 返回 `None`（已实测）。

**验证**：`script_library` 70/70、`script_catalog` 56/56、`skill_refs` 22/22、`structure` 41/41；
实测真实库 `files=137`／`sections=2333`／`unindexedFiles=0`／`dirs` 为两个来源目录，
`skill=` 三种写法结果一致（86 命中）。顺带查实新旧两种 `path_contains`：`combat/` 73 命中、
`library/combat` **0 命中** —— 两个 SKILL.md 里照抄旧写法的检索示例已一并改成
`path_contains="combat/"`／`"ultimate/"`（带斜杠才不连 `modules/combat.md`、`modules/ultimate.md`
两份规约摘要一起捞进来），这是本次改造里唯一会让人「按文档搜不到东西」的实质缺陷。

比内容永远输**。而加索引本来是为了让人找得到，结果先把检索顶掉了。

**修法：降权，不排除**（`script_library.PLAYBOOK_NAV_DOCS` ＝ 3 份点名名单，`PLAYBOOK_NAV_WEIGHT = 0.3`）。
0.3 是算出来的不是拍的：真资料单词命中 6 分上下，索引能到 10~11 分，乘 0.3 落到 3~3.3，稳定排后面。
**写成点名名单而不是「文件名含『索引』」的规则** —— 后者会误伤名字里带「索引」的真资料，
也会让以后新增的索引文档静默漏网（漏网必须在测试里报出来，所以名单得显式）。

**留了一个出口**：`PLAYBOOK_NAV_INTENT = ("索引", "目录", "index")`，查询本身带这些词时不打折。
否则「资料索引」这种明确意图会被真资料顶掉。实测 `资料索引` 命中：`打戏系统资料索引` 5.0 排第 2、
`通用资料索引` 5.0 排第 3，都能找到。

**固化**：`script_library_test.py` 再加 **5 条**（73 → 78）—— 名单每份真实存在（改名即静默失效）／
`造型` `特效` `运镜` 三个族名第一条必须是方法正文／明确找目录时索引仍排得上前 5。
**反向验证过**：把 `PLAYBOOK_NAV_WEIGHT` 临时改回 `1.0`，`造型` 那条报
`<<< 'film-expert-bridge/general/通用资料索引.md'`，精确指出是它霸了榜；复原后 78/78。

**发现但本轮不修**：`打戏索引` 这种查询 **`matched = 0`** —— `query_terms` 中文不切词、整串当一个词，

### 9.9 我自己写的「假绿灯」（2026-11-06）

补最后一道没验过的闭环：**检索回执给的 `path`，`open_document` 能不能真打开**。实测 10 个查询

那一刻才是本轮真正的收获：**判据本身错了。** 我写的是

if not _resp or _resp.get("available") is False:
```

hint="索引里没有这份文件的正文记录（目录里也没有）"
```

**肉眼一看就是打不开，判据却因为 `available=True` 放过去了。** 判「打得开」必须判**回执里

### 9.10 只对「合计」，等于没对（2026-11-06）

回头审自己的断言时发现 §9.7 那条第 73 号漏洞：

```python
check("... §1 族表份数合计 == 该层实际原料数（份数写错就是骗人）", _tot == len(_real), ...)
```

**它只比合计。** 而 §1 的用途是「照着族名去取那几份」—— 角色造型多报 2、场景少报 2，
合计照样 38 == 38，**报错的那两族没人管**。我写这条时想的是「数错了就骗人」，落地时
只落了「总数」，没落「每族」。

补四条对账（前三条不依赖族名，判据写在 `script_library_test.py`）：

| 判据 | 抓什么 |
|---|---|
| 每节抬头「（N 份）」== 该节真正点名的**本层**文件数 | 某族自己声明错，或表里少列一份 |
| §1 十行数字与各小节声明数字**排序后**相同 | 两处数字互相抵消（只对合计时看不见） |
| 38 份每份都归且只归一个「带份数声明的节」 | 有的文件谁都不归属（索引里查不到它）／重复归属 |
| 抬头「**十**族一览（合计 **38** 份）」里的两个散文数字 == 表行数 == 盘上文件数 | 「十族」写成「十一族」（**这个错真发生过一次**，当时靠人眼翻出来） |

**为什么不按族名 join**：§1 写「画法与底层方法」，§7 抬头写「画法方法」—— 按名字对其实
差一个字，往后谁再改名就静默失效。这正是 §9.8「点名名单要显式」的反面教训：**能用结构定的
就别用名字定**。「抬头声明了（N 份）」这件事本身就是结构信号，§0/§1/§11/§12 都没有声明。

两个实现细节（都会让判据变成假绿）：
- **只算本层文件**：§3 声明 6 份、却列了 7 个 `.md`，多出来的是 `../modules/shot_grammar.md`。
  带 `/` 的一律不算——那是跨层引用，不是本级的份数。
- **§7 是两族合写**（「动作与打斗（2 份）＋ 画法方法（2 份）」），声明数取该行**所有**「（N 份）」之和 = 4。

**反向验证两种坏法**（都只动 `corpus/playbook/` 里那一个 md，改完全字节复原）：
1. **两错相消**：角色造型 `7→9`、场景 `4→2`（合计仍 38）⇒ **合计判据 PASS**、多重集判据
   **FAIL**，detail 直接摊出 `[2,2,2,2,2,4,4,5,6,9]` 与 `[2,2,2,2,4,4,4,5,6,7]`；81/82。
2. **小节自声明错**：§5 抬头 `场景（4 份）→（5 份）` ⇒ 两条新判据都 FAIL（`('份数不符','5. 场景（5 份）',5,4)`），
   **合计判据仍 PASS**；80/82。
3. **散文数字错**（历史上真出现的那个）：`十族→十一族` ⇒ FAIL，detail `(('十一','38'), 10, 38)`；82/83。

> 第 1 种坏法正是这条漏洞的形状：**旧判据在坏状态下依然 PASS**。同一个数字，我问的是
> 「加起来对不对」，该问的是「每一族对不对」——**合计是投影，族才是本体。**

**这轮还踩了自己一次**：新断言第一次跑就报红，`('份数不符', ..., 5, 0)` —— 列出数全是 0。
不是文档错，是我把正则写成 `` `([^`]+?)\.md` ``，`.md` 落在了捕获组**外面**，取到
「分镜图规范库」而不是「分镜图规范库.md」，`n in _real_names` 全部落空。放回组内即 82/82。
与 §9.9 恰好相反：那次判据太松（该红却绿），这次判据坏了（该绿却红）—— **两次都是「立刻跑、
并且读 detail」才发现的**。只报颜色不读 detail，红的会被当成文档错、绿的会被当成验过了。

## ⭐⭐ H3 **混合打包形态**（关键帧 + 参考块一起给）此前一条用例都没有 ✗
`h3_form.packed_layout` 的文档里段序就写着 `text → [cond* / cond_audio*] → [ref_img* / ref_audio*]
→ audio → video` ✓（**支持两类一起给** ✓），但自检里只有「**只给**关键帧」✓ 与「**只给**参考块」✓
两条各自的路 ✗ —— 而现实里「首帧 + 参考图 + 参考视频（带音轨）」是常用组合 ✓，且两种块**混在一起
不会报错** ✓✗（正是静默错最爱藏的地方 ✓）⇒ 补 4 条（`engine_h3_form_test` 70 → **74 项** ✓）：

* ㉒⁶ 段序（cond 在 ref 之前 ✓、目标两条流仍在最后 ✓ audio 在 video 前 ✓）；
* ㉒⁷ 时间轴对账 ✓：`cursor = text_len + Σ参考跨度` ✓ —— **参考块推后 ✓、条件块不推后** ✗✗
  （cond 的 t = `cursor + FRAME_RESCALE×frame_index` ✓ —— 两种块混在一起时最容易写错 ✓）；
* ㉒⁸ 行数对账（块清单 ↔ 段表 ✓）+ 更新掩码的长度与归属 ✓；
* ㉒⁹ 行序**「能失败」**✓：对调两个关键帧的源 ⇒ 视频行与音频行**都要变** ✓；缺参考块的源 ⇒ 报错 ✓。

### 写这几条时踩的坑（都是夹具/断言，不是产品 ✗）
1. 关键帧的潜尺寸要按**目标网格**给 ✓（事实：cond 用**目标**空间网格 ✓）—— 给 (2,2,2,2) 会算成 2 行
   而布局要 8 行 ✓✗；
2. `assemble_blocks` 用**同一份** `patch_size` 切所有块 ✓ ⇒ 参考块的**潜通道数**也得等于
   `latents_dim` ✓（给 1 会让 `torch.cat` 报"尺寸不一致" ✗ —— 那报的是形状错，验不到"顺序" ✓）；
3. ⚠️ 「对调源 ⇒ 行必变」要换**同形**的两个块 ✓（参考块 1 行 vs 8 行，对调先撞行数校验 ✗✗）；
4. ⚠️ 视频源与音频源**各自都要换** ✓✗（只换视频 ⇒ 音频行当然不变 ✓ —— 我第一版就这么红的 ✓）。

## ⚠️⚠️ 一个**坐标空间**的坑（产品文档缺一句，我自己先撞上 ✗）
`packed_layout` 返回的 `segments` 是**序列坐标** ✓（含 text 行 ✓，长度 = `seq_len` ✓）；
而 `img_update` / `audio_update` 是**打包坐标** ✓（只按视频行 / 音频行打包 ✓ **不含 text 行** ✗✗）——
长度 = 目标行数 + 非目标同流块行数 ✓。⇒ **拿 `segments` 的下标去切掩码必错位** ✓✗，而且**不报错**
（只会"某些行该更新却没更新" ✓✗）。
⚠️ 这不是产品 bug ✓（打包空间是有意的 ✓：`H3FormTrunk.forward` 里再拼一次目标 ✓）—— 但文档没写清 ✗
⇒ 已在 `packed_layout` 的 docstring 里补一段**显式警告** ✓（含"自检里自己就混过"这条 ✓）。
